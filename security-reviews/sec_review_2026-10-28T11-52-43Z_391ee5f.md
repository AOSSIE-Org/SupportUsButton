## Findings

### Finding 1: Script injection in `pull_request_target` workflow via attacker-controlled PR file names — `.github/workflows/sync-pr-labels.yml:140`

- Severity: High
- Confidence: 0.9
- Category: ci_script_injection
- Description: The "Sync PR Labels" workflow runs on `pull_request_target` (base-repo
  context, write-scoped `GITHUB_TOKEN` with `pull-requests: write` and `issues: write`,
  and access to repository secrets). The "Get changed files" step (line 114-132)
  collects the file names of the PR via `pulls.listFiles` and emits them with
  `core.setOutput('files', JSON.stringify(changedFiles))`. The next step then
  interpolates that output with a GitHub expression directly into the JavaScript
  source of an `actions/github-script` step:
  `const changedFiles = JSON.parse('${{ steps.changed-files.outputs.files }}');`.
  Expressions are substituted textually before the script is evaluated, and
  `JSON.stringify` does not escape single quotes. Git permits `'`, `(`, `)`, `;`
  and spaces in file names, and the file names are fully chosen by whoever opens the
  pull request (including from a fork). A file name containing a single quote
  therefore terminates the string literal and the rest of the name is evaluated as
  JavaScript inside the privileged job. The job guard
  `github.repository_owner == 'AOSSIE-Org'` does not help: it is true for every PR
  opened against the upstream repository, and `pull_request_target` runs for fork PRs
  without needing the PR to be merged.
- Exploit Scenario: An attacker forks the repository and adds a file whose name
  closes the string literal, runs an arbitrary JavaScript statement, and re-opens a
  string so the remainder of the line still parses. Opening (or pushing to) the PR
  triggers the workflow; the injected code runs with the authenticated `github`
  Octokit client and `GITHUB_TOKEN`, letting the attacker edit or close issues and
  PRs, add/remove labels (including spoofing `coderabbit-approved`), and post
  comments as the repository bot. Because the code runs on the job's runner, it can
  also tamper with the runner's files (for example the cached `actions/github-script`
  code used by later steps), which puts the `EXTERNAL_LABELLER_TOKEN` secret passed to
  the "Apply contributor-based labels" step (line 262-267) at risk of exfiltration;
  the impact of that depends on the scopes of that token, which could not be checked
  from the repository.
- Recommendation: Never interpolate step outputs or event data into a
  `github-script` `script:` body. Pass the value through `env:` and read it at run
  time, e.g. `env: { CHANGED_FILES: ${{ steps.changed-files.outputs.files }} }` and
  `const changedFiles = JSON.parse(process.env.CHANGED_FILES);`, or simply merge the
  two steps and call `pulls.listFiles` (with pagination) in the same script so no
  cross-step interpolation is needed. Apply the same `env:` pattern to the other
  `'${{ steps.*.outputs.* }}'` interpolations in this workflow (line 65) and in
  `coderabbit-approval.yml` (line 121) for consistency, even though those values are
  currently constrained to digits or `true`/`false`.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at
  runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues
  cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated
  statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails
  built into some models can cause a real vulnerability to be softened, generalized,
  or left out rather than reported in exploit-level detail, and training-data bias can
  make some vulnerability classes easier for a model to recognize than others. Treat
  this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to
  a very recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations**

- Finding 1: a concrete payload file name was deliberately not included; the
  description gives the mechanism and the fix only.
- The scopes and owner of the `EXTERNAL_LABELLER_TOKEN` secret, and the repository's
  Actions settings (e.g. fork-PR approval policy, default token permissions), are not
  visible from the repository, so the full blast radius of Finding 1 could not be
  determined.
- Third-party actions referenced by tag (e.g. `eps1lon/actions-label-merge-conflict@v3`,
  `AndreasAugustin/actions-template-sync@v2`, `release-drafter/release-drafter@v6`)
  were not inspected; their source was out of scope and unavailable.
- Dependency versions in `package.json` were not checked against advisories, and
  `package-lock.json`, `node_modules/` and `dist/` were excluded by request.
